# Mini NPU 시뮬레이터

숫자로 표현한 패턴과 필터를 비교하는 Python 콘솔 프로그램입니다.

같은 위치의 값을 곱하고 모두 더하는 MAC 연산을 직접 구현했습니다.
사용자 입력과 JSON 분석을 지원하며, 오류 처리와 성능 측정을 포함합니다.
보너스 기능으로 패턴 자동 생성과 1차원·2차원 배열의 성능 비교를 구현했습니다.

## 1. 개발 환경

- Python 3.8 이상
- Python 표준 라이브러리만 사용
- NumPy, pandas 등 외부 라이브러리 사용 없음
- 실행 확인 환경: Windows PowerShell, VS Code

사용한 주요 표준 라이브러리는 다음과 같습니다.

| 라이브러리 | 용도 |
|---|---|
| json | JSON 파일 읽기와 저장 |
| time | MAC 연산 시간 측정 |
| math | 유한수 검사 |
| re | 패턴 키 형식 검증 |
| pathlib | 파일 경로 처리 |
| copy | 검증용 데이터 복사 |
| unittest.mock | 원본 파일 변경 없이 오류 데이터 전달 |

## 2. 파일 구성

아래 파일을 같은 폴더에 둡니다.

| 파일 | 역할 |
|---|---|
| main.py | 입력 방식 선택, MAC 계산, 판정, JSON 분석, 성능 분석 |
| create_data.py | 크기 입력 기반 패턴 생성, 연습용 JSON 생성 |
| data.json | 크기별 필터와 판별할 패턴 |
| test_errors.py | 오류 데이터 처리와 epsilon 비교 검증 |

| benchmark_compare.py | 1차원·2차원 MAC의 정확도와 성능 비교 |

main.py와 benchmark_compare.py는 create_data.py의 생성 함수를 가져와 사용합니다.
따라서 main.py만 따로 옮기면 실행되지 않으며, 관련 파일을 함께 제출해야 합니다.

## 3. 실행 방법

프로젝트 폴더에서 터미널을 엽니다.

Windows에서는 다음 명령어를 사용합니다.

```powershell
py main.py
```

환경에 따라 다음 명령어를 사용할 수도 있습니다.

```bash
python main.py
```

Linux/macOS에서는 Python 설치 환경에 따라 python3를 사용합니다.

```bash
python3 main.py
```

### 사용자 입력 모드

메뉴에서 1을 선택합니다.

필터 A, 필터 B, 입력 패턴을 각각 3행씩 입력합니다.
각 행에는 숫자 3개를 공백으로 구분해 입력합니다.

필터 A 예시:

```text
0 1 0
1 1 1
0 1 0
```

필터 B 예시:

```text
1 0 1
0 1 0
1 0 1
```

입력 패턴 예시:

```text
0 1 0
1 1 1
0 1 0
```

예상 결과:

```text
A 점수: 5
B 점수: 1
최종 판정: A
```

두 필터의 MAC 연산 시간과 3×3 성능 분석도 출력합니다.

숫자 개수가 다르거나 숫자가 아닌 값을 입력하면 해당 행을 다시 요청합니다.
nan, inf와 같은 비유한 값도 입력에서 거부합니다.

### JSON 분석 모드

main.py 메뉴에서 2를 선택합니다.

프로그램은 main.py와 같은 폴더에 있는 data.json을 읽습니다.
각 케이스의 점수, 판정, 정답, PASS/FAIL을 출력합니다.
이후 크기별 성능 표와 전체·통과·실패 수, 실패 사유를 출력합니다.

분석이 끝나면 메뉴로 돌아옵니다.
메뉴에서 0을 선택하면 종료합니다.

### 연습용 데이터 생성

data.json이 없는 경우 다음 명령어를 실행합니다.

```powershell
py create_data.py
```

메뉴에서 2를 선택하면 5×5, 13×13, 25×25 필터와 정상 패턴 6개를 생성합니다.

기존 data.json이 있으면 덮어쓰지 않습니다.
현재 데이터는 과제에서 제공된 파일이 아니라 직접 생성한 연습용 데이터입니다.

### 크기 입력 기반 패턴 생성

```powershell
py create_data.py
```

메뉴에서 1을 선택하고 양의 홀수 N을 입력합니다.
예를 들어 5를 입력하면 5×5 십자가와 X를 출력합니다.

가운데 행과 열이 명확하도록 양의 홀수만 허용합니다.
짝수, 음수, 숫자가 아닌 입력은 안내 후 재입력을 요청합니다.
크기 입력에서 0은 취소입니다.

### 오류 처리와 epsilon 검증

```powershell
py test_errors.py
```

원본 데이터를 복사한 뒤 오류 케이스를 추가해 분석합니다.
unittest.mock으로 파일 읽기를 대체하므로 원본 data.json은 바뀌지 않습니다.

### 1차원·2차원 성능 비교

```powershell
py benchmark_compare.py
```

크기별 계산 결과 일치 여부와 두 방식의 평균 시간을 출력합니다.

## 4. 데이터 구조와 키 규칙

패턴과 필터는 숫자를 담은 리스트 안에 행별 리스트를 넣어 저장합니다.

```python
pattern = [
    [0, 1, 0],
    [1, 1, 1],
    [0, 1, 0],
]
```

Python의 위치 번호는 0부터 시작합니다.

```python
pattern[0][1]       # 첫 번째 행, 두 번째 열 읽기
pattern[0][1] = 1   # 해당 위치에 값 저장
```

JSON의 주요 구성은 다음과 같습니다.

| 항목 | 의미 |
|---|---|
| filters | 크기별 필터 묶음 |
| filters의 size_5 | 5×5 필터 묶음 |
| cross, x | 필터 이름 |
| patterns | 판별할 패턴 묶음 |
| size_13_2 | 13×13 크기의 두 번째 패턴 |
| input | 입력 숫자 배열 |
| expected | 정답 라벨 |

패턴 키는 size_N_idx 형식으로 읽습니다.
N과 idx는 1 이상의 정수입니다.
키에서 N을 추출해 filters의 size_N 필터를 선택합니다.

패턴과 필터의 행 수, 각 행의 열 수, 값의 자료형과 유한성을 검사합니다.
Python에서 숫자의 하위 유형인 bool도 데이터 검증에서는 거부합니다.
크기 불일치나 필수 항목 누락은 해당 케이스의 FAIL로 기록합니다.

## 5. MAC 연산 구현

MAC은 Multiply-Accumulate의 약자로, 곱한 값을 누적해 더하는 계산입니다.

패턴과 필터에서 같은 위치의 숫자를 곱하고 모든 결과를 더합니다.

```python
total = 0.0

for row in range(len(pattern)):
    for col in range(len(pattern[row])):
        total += pattern[row][col] * filter_matrix[row][col]
```

외부 라이브러리 없이 반복문으로 구현했습니다.

3×3 십자가 패턴을 십자가 필터와 비교하면 5점입니다.
같은 패턴을 X 필터와 비교하면 가운데 위치만 겹쳐 1점입니다.

이 점수는 원소별 곱의 합이며, 일치율이나 확률을 의미하지 않습니다.

## 6. 라벨 정규화와 판정 정책

내부 비교에 사용하는 표준 라벨은 Cross와 X입니다.

| 원래 표기 | 표준 라벨 |
|---|---|
| + | Cross |
| cross | Cross |
| Cross | Cross |
| x | X |
| X | X |

문자열 앞뒤 공백과 영문 대소문자 차이를 정리한 뒤 변환합니다.
지원하지 않는 라벨은 임의로 추측하지 않고 오류로 기록합니다.
새 표기나 분류를 추가하는 절차와 자동 테스트는 **13절: 라벨 확장 절차**에 설명합니다.

점수 비교에는 다음 기준을 적용합니다.

```python
EPSILON = 1e-9

abs(score_a - score_b) < EPSILON
```

두 점수 차이의 절댓값이 EPSILON보다 작으면 UNDECIDED로 판정합니다.
이 구현은 `<`를 사용하므로 차이가 정확히 EPSILON이면 동점 조건에 포함하지 않습니다.

사용자 입력 모드의 승자 표시는 A 또는 B입니다.
JSON 모드의 승자 표시는 Cross 또는 X입니다.
JSON의 표준화된 정답과 판정이 같으면 PASS, 다르면 FAIL입니다.

정답이 Cross 또는 X일 때 UNDECIDED는 FAIL입니다.

## 8. 오류 데이터 및 수치 비교 검증

기본 데이터 6개에 의도적인 실패 케이스 5개와 마지막 정상 케이스 1개를 추가했습니다.

| 추가 케이스 | 조건 | 실제 결과 |
|---|---|---|
| size_5_3 | 5×5 패턴의 행이 4개 | 크기 오류 FAIL |
| size_5_4 | expected가 triangle | 라벨 오류 FAIL |
| wrong_key | 키 형식 불일치 | 키 오류 FAIL |
| size_5_5 | expected 누락 | 필수 항목 오류 FAIL |
| size_5_6 | 모든 값이 1, 정답은 Cross | 동점 UNDECIDED → FAIL |
| size_5_99 | 오류 뒤에 배치한 정상 패턴 | PASS |

실제 집계는 전체 12개, 통과 7개, 실패 5개였습니다.
의도한 오류를 발견하고 마지막 정상 케이스까지 처리했으므로 오류 처리 검증은 성공했습니다.

epsilon 비교도 별도로 확인했습니다.

| 조건 | 실제 결과 | 검증 |
|---|---|---|
| 1.0과 1.0 | UNDECIDED | PASS |
| 1.0 + 5e-10과 1.0 | UNDECIDED | PASS |
| 1.0 + 2e-9와 1.0 | A | PASS |
| 1.0과 2.0 | B | PASS |

이 검증은 epsilon보다 작은 차이와 큰 차이를 확인했습니다.
정확한 경계값 동작은 코드의 `<` 정책으로 명시했으며, 위 네 사례에 경계값 검증은 포함하지 않았습니다.

사용자 입력에서도 숫자 개수 부족과 문자 입력 후 같은 행을 다시 요청하는 동작을 확인했습니다.

## 9. 성능 측정 방법과 결과

time.perf_counter()로 MAC 함수 호출 구간을 측정했습니다.

- 입력·출력·파일 읽기 시간 제외
- 패턴 생성 시간 제외
- 측정 전 10회 준비 실행
- 크기별 1,000회 측정 후 1회 평균 시간 계산
- 생성기로 만든 십자가 패턴과 십자가 필터 사용
- 필터 하나에 대한 MAC 계산을 기준으로 비교

정상 JSON 분석 실행에서 얻은 측정 예시는 다음과 같습니다.

| 크기 | 평균 시간(ms) | MAC 횟수 N² |
|---|---:|---:|
| 3×3 | 0.000586 | 9 |
| 5×5 | 0.001266 | 25 |
| 13×13 | 0.005513 | 169 |
| 25×25 | 0.017895 | 625 |

시간은 실행 환경과 측정 시점에 따라 달라집니다.
짧은 연산이므로 시간 측정 호출 자체의 비용도 결과에 영향을 줍니다.

## 10. 보너스: 1차원 배열 성능 비교

2차원 배열을 행 순서대로 펼쳐 길이 N²의 1차원 배열로 변환했습니다.
1차원 MAC도 반복문으로 직접 구현했습니다.

정확도 검증은 각 크기에서 다음 네 조합으로 수행했습니다.

- Cross 패턴 × Cross 필터
- Cross 패턴 × X 필터
- X 패턴 × Cross 필터
- X 패턴 × X 필터

4개 크기에서 총 16개 조합의 점수가 모두 일치했습니다.

성능 비교는 동일한 십자가 패턴과 필터를 사용했습니다.
두 방식 모두 라운드당 1,000회씩 5라운드 측정했습니다.
라운드마다 측정 순서를 번갈아 바꾸었습니다.
패턴 생성과 1차원 변환은 측정 전에 수행했습니다.

| 크기 | 2차원 평균(ms) | 1차원 평균(ms) | 2차원 시간 ÷ 1차원 시간 |
|---|---:|---:|---:|
| 3×3 | 0.000520 | 0.000296 | 1.75 |
| 5×5 | 0.001047 | 0.000663 | 1.58 |
| 13×13 | 0.005502 | 0.003707 | 1.48 |
| 25×25 | 0.017756 | 0.014714 | 1.21 |

시간 비율은 반올림 전 측정값으로 계산한 출력값입니다.

이번 측정에서는 모든 크기에서 1차원 방식의 평균 시간이 짧았습니다.
1차원 구현은 중첩 반복문과 이중 인덱싱을 줄였으며, 이것이 시간 차이에 기여했을 수 있습니다.
이 실험만으로 하드웨어 캐시 효과를 분리해 입증한 것은 아닙니다.

위 비교는 MAC 함수 실행 시간을 대상으로 합니다.
배열 변환 시간과 추가 메모리 비용을 포함한 전체 처리 시간의 개선을 보장하지는 않습니다.

## 11. 결과 리포트

1. 정상 데이터 6개를 분석한 결과, 전체 6개가 PASS했고 실패는 0개였습니다.
2. 이 데이터는 생성한 필터와 대응하는 정상 패턴으로 구성되어 있어 해당 패턴의 점수가 더 높게 계산되었습니다.
3. expected의 +와 필터 키 cross를 모두 Cross로 통일해 표기 차이로 인한 잘못된 FAIL을 방지했습니다.
4. x와 X도 동일한 표준 라벨 X로 비교하도록 구성했습니다.
5. epsilon 정책은 부동소수점의 아주 작은 점수 차이를 동점으로 취급하기 위한 기준입니다.
6. 정상 데이터의 점수는 정수이므로 이번 0 FAIL 결과가 epsilon 덕분이라고 단정할 수는 없습니다.
7. epsilon보다 작은 차이를 별도 검증했고, UNDECIDED가 반환되는 것을 확인했습니다.
8. 행 개수 불일치, 잘못된 키, 필수 항목 누락은 데이터·스키마 문제로 진단했습니다.
9. 지원하지 않는 라벨은 라벨 규칙 위반이며, 정규화로 임의의 정답으로 바꾸지 않고 FAIL로 처리했습니다.
10. 모든 칸이 1인 패턴은 두 필터 점수가 같으므로 UNDECIDED가 정상적인 계산 결과입니다.
11. 이 동점 패턴의 expected가 Cross이면 FAIL이며, 이를 없애기 위해 임의로 Cross를 선택하지 않았습니다.
12. 의도한 실패 5개 뒤의 정상 케이스도 PASS해, 케이스 단위 오류가 전체 분석을 중단시키지 않음을 확인했습니다.
13. 전체 12개, 통과 7개, 실패 5개로 집계가 일치했습니다.
14. N×N 배열은 N개의 행에서 각각 N개의 열을 방문하므로 필터 하나당 N²번의 곱셈·누적 단계를 수행합니다.
15. 따라서 MAC 함수의 시간 복잡도는 O(N²)이며, N이 두 배가 되면 처리 위치는 네 배가 됩니다.
16. 필터 두 개의 계산량은 2N²이지만, 상수 계수를 제외한 시간 복잡도는 여전히 O(N²)입니다.
17. 실제 측정에서도 배열이 커질수록 평균 시간이 증가했지만, 측정 비용과 실행 환경 때문에 시간 비율이 N² 비율과 정확히 같지는 않았습니다.
18. 1차원으로 펼쳐도 처리할 원소는 N²개이므로 시간 복잡도는 O(N²)로 같습니다.
19. 1차원·2차원 계산 결과는 16개 조합에서 일치했고, 이번 측정에서는 1차원의 평균 시간이 더 짧았습니다.
20. 패턴 생성과 배열 펼치기 역시 원소 수만큼 처리하므로 O(N²) 시간이 필요하며, 이 시간은 MAC 성능 비교에서 제외했습니다.
21. 배열 저장에는 O(N²) 공간이 필요하고, MAC 함수 자체의 추가 누적 공간은 O(1)입니다.
22. 1차원 배열을 별도로 만들면 기존 2차원 배열 외에 O(N²)의 추가 저장 공간이 필요합니다.

## 12. 한계와 해석

이 프로그램은 사람이 정한 필터로 점수를 계산하는 학습용 시뮬레이터입니다.
데이터로 필터를 학습하는 기능이나 실제 NPU의 병렬 실행은 구현하지 않았습니다.
CPU·NPU 관점의 병렬화 지점, 예상 병목과 최적화 우선순위는 **14절**에 설명합니다.

MAC 점수가 높다는 것은 해당 필터의 가중치와 입력값의 곱의 합이 크다는 뜻입니다.
모든 종류의 이미지에서 올바른 모양을 판별한다는 보장은 없습니다.

원시 점수는 입력값과 필터값의 크기에도 영향을 받습니다.
정규화된 유사도나 확률로 해석해서는 안 됩니다.

성능 실험은 Python 실행 시간 비교이며, 실제 NPU 성능을 나타내지 않습니다.
두 방식의 실행 시간 차이는 해당 환경에서 관찰한 결과로 해석합니다.

## 13. 라벨 확장 절차 (평가 항목 #18 보완)

**새로운 모양의 분류**인지 구분합니다.

6. 동일한 크기에 `cross`와 `plus` 필터를 동시에 넣었을 때는 둘 다 Cross가 되어 중복 오류가 발생하는지 확인합니다. 별칭 추가로 필터가 조용히 덮어써지면 안 됩니다.


## 14. CPU·NPU 처리 방식과 예상 병목 (평가 항목 #20 보완)

### 14.1 현재 코드에서 직렬 처리되는 부분

현재 `mac_2d()`는 Python 반복문으로 한 위치의 값을 읽고 곱한 뒤
`total`에 더하는 작업을 순서대로 수행합니다.
`run_json()` 역시 패턴을 하나씩 처리하고, Cross와 X 점수를 차례로 계산합니다.

이것은 **현재 구현이 직렬이라는 뜻**입니다.
CPU 자체가 직렬 연산만 가능한 것은 아닙니다.
현대 CPU는 여러 코어와 SIMD 명령으로 병렬 계산도 수행할 수 있습니다.
현재 코드에서는 그러한 병렬 실행을 직접 구성하지 않았습니다.

### 14.2 병렬화할 수 있는 위치와 이득

25×25 필터 두 개를 비교하면 총 1,250개 위치의 곱셈·누적을 수행합니다.
각 위치의 곱셈은 서로 독립적이므로 여러 연산기에 분배할 수 있습니다.
각 연산기가 부분합을 계산한 뒤 이를 합치는 reduction(합산) 단계가 필요합니다.
서로 다른 필터나 서로 다른 패턴도 데이터 의존성이 없으면 병렬 처리할 수 있습니다.

NPU는 이러한 반복 MAC을 여러 연산기에서 처리하고 데이터를 재사용하도록 설계할 수 있습니다.
이득은 계산할 총 원소 수가 줄어서가 아니라, 많은 계산을 동시에 진행하는 데서 나옵니다.
원소별 곱셈을 동시에 처리해도 결과 합산, 메모리 공급, 실행 준비 비용은 남습니다.
부동소수점은 합산 순서가 바뀌면 작은 차이가 생길 수 있으므로 병렬화 후에도
점수 비교 정책과 정확도 재검증이 필요합니다.

### 14.3 어디가 병목이 될 수 있는가

병목은 전체 속도를 제한하는 지점입니다.
다음은 코드 구조와 하드웨어 동작을 바탕으로 한 **예상 분석**이며,
현재 실험에서 각 비용을 분리해 측정한 결과는 아닙니다.

| 예상 병목 | 현재 Python CPU 구현 | 병렬 NPU 실행을 가정한 경우 | 우선 검토할 개선 |
|---|---|---|---|
| 반복·인덱싱 비용 | 반복문, 리스트 접근, 숫자 객체 연산을 매 위치마다 수행 | 지원되는 연산을 전용 연산기에 묶어 실행 가능 | 현재 구현에서는 1차원 접근과 반복 구조 단순화 |
| 누적합 의존성 | 다음 total 갱신이 이전 값에 의존 | 독립 부분합을 병렬 계산한 뒤 합산 필요 | 부분합 분할과 합산 비용·오차 검증 |
| 메모리 대역폭·지연 | 배열이 커지면 값을 가져오는 비용이 영향 | 연산기가 많아도 데이터 공급이 느리면 대기 | 입력·필터 재사용, 데이터 이동 감소 |
| 실행 준비·전송 비용 | 함수 호출과 시간 측정 비용이 작은 작업에 영향 | 장치 준비, 버퍼 구성, 동기화와 필요 시 데이터 복사 비용 발생 | 작은 연산을 묶어 처리하되 전체 지연도 비교 |
| 병렬 자원 활용률 | 현재 코드는 패턴·필터를 순서대로 처리 | 작업이 너무 작으면 연산기를 충분히 활용하기 어려움 | 여러 패턴·필터를 묶는 배치 처리 검토 |
| 파일·출력 비용 | 실제 전체 실행에서는 JSON 읽기와 콘솔 출력도 시간 소요 | 장치를 빨리 해도 호스트의 파일·출력 비용은 남음 | 연산 시간과 전체 실행 시간을 구분 |

NPU도 메모리에서 값을 충분히 공급받지 못하면 메모리 병목이 생깁니다.
실제 병목은 데이터 크기, 재사용 정도, 메모리 구조, 지원 연산에 따라 달라집니다.
공유 메모리 장치도 있으므로 모든 NPU가 별도 장치 복사를 요구한다고 가정하지 않습니다.

### 14.4 병렬 처리 시간의 단순 모델

아래 식은 설명용 모델이며 실측 NPU 성능 예측식은 아닙니다.

```text
전체 지연 ≈ 준비·데이터 이동 시간
          + 병렬화할 수 없는 작업 시간
          + 병렬 계산 시간
          + 부분합 합산·동기화 시간

이상적인 병렬 계산 시간 ≈ 해당 계산의 직렬 시간 ÷ 유효 병렬 처리 수
```

예를 들어 1,250개 MAC을 P개 연산기에 분배하더라도 전체 시간이 항상 1/P이 되지는 않습니다.
직렬 구간, 합산, 데이터 대기, 자원 미활용 때문에 실제 이득은 제한됩니다.
특히 3×3처럼 작은 작업은 실행 준비 비용이 병렬화 이득보다 클 수 있습니다.
병렬화는 총 MAC 수나 현재 알고리즘의 작업량 O(N²)를 없애지 않습니다.

### 14.5 이 프로젝트의 단기 최적화 우선순위

1. 정규화, 크기 검증, epsilon 정책과 정상·오류 케이스를 먼저 유지합니다.
2. 동일 입력·동일 반복 횟수로 기준 시간을 측정하고, 타이머 비용을 줄인 반복 묶음 측정도 검토합니다.
3. 이미 구현한 1차원 배열 방식으로 반복과 접근 구조를 단순화하고 정확도를 재검증합니다.
4. 같은 배열을 재사용할 때 펼치기 결과를 재사용해 반복 변환을 줄입니다. 변환을 포함한 전체 시간과 추가 메모리도 따로 확인합니다.
5. 그다음 실제 사용 규모에서 병목을 프로파일링합니다. 여러 패턴의 배치나 필터 재사용을 우선 검토합니다.
6. NPU를 사용할 후속 실험에서는 지원 연산과 자료형을 확인하고, 전송·준비·합산을 포함한 전체 시간까지 같은 조건으로 측정합니다.

현재 1차원 비교의 이득은 CPU에서 실행한 Python 코드의 관찰 결과입니다.
이를 NPU의 병렬 가속 배수나 캐시 개선의 직접 증거로 해석하지 않습니다.
현재 프로그램에는 실제 NPU 실행이 없으며, 위 병렬화 내용은 후속 설계 분석입니다.
